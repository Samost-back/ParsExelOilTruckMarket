# ParsExelOilTruckMarket

Платформа автоматизації товарного каталогу мастил: від прайс-листа постачальника
до опублікованого оголошення на маркетплейсі TruckMarket — з обробкою фото,
генерацією описів через AI та повним контролем процесу через веб-панель.

Система забирає на себе рутину, через яку менеджер інакше витрачав би години:
ручне перенесення позицій з Excel, підготовку фотографій під єдиний стандарт,
написання описів і заповнення карток на маркетплейсі. Замість цього — завантажив
прайс і папку з фото, переглянув зведення змін, опублікував.

---

## Що вирішує продукт

Постачальники мастил надсилають прайси в різних форматах Excel, фотографії товарів —
окремими файлами без прив'язки до позицій, а маркетплейс вимагає структуровані
картки з характеристиками, фото в єдиному вигляді й коректну геолокацію. Між цими
полюсами — багато ручної, помилконебезпечної роботи.

Платформа закриває весь цей ланцюг:

- **Імпорт і оновлення** — парсинг прайсу, розпізнавання змін (нові позиції,
  зміни цін, оновлення характеристик), ведення історії цін.
- **Обробка фотографій** — автоматичне накладання товару на стандартний шаблон
  тари (каністра/бочка/відро) з чіткими інформаційними плашками.
- **AI-описи** — генерація продаючого опису з усіх характеристик товару, з
  редагованим промптом і симулятором попереднього перегляду.
- **Публікація на TruckMarket** — формування картки під вимоги API маркетплейсу,
  завантаження фото, коректна геолокація, ведення статусу публікації.
- **Контроль** — кожна дія виконується як фонова задача з покроковим статусом,
  живим логом і картку-зведенням результату.

## Архітектура

Моноліт на Node.js із чітким поділом на bounded contexts. Єдине джерело
правди — PostgreSQL; усе, що відбувається, проходить через базу.

```
Excel прайс  ─┐
              ├─► [Парсер] ─► [save-oils: diff + історія цін] ─► PostgreSQL ─┐
Папка фото   ─┘                                                              │
                                                                            ▼
                         [Обробка фото (sharp + SVG-плашки)] ◄──────────────┤
                                                                            │
                              [AI-описи (OpenAI)] ◄──────────────────────────┤
                                                                            ▼
                         [TruckMarket-оркестратор] ─► картка + фото ─► Маркетплейс
```

Поверх усього — веб-панель (Fastify + EJS + HTMX), яка керує процесами та
показує стан. Важкі операції не блокують інтерфейс: вони виконуються як фонові
задачі з потоковою трансляцією логів у браузер (Server-Sent Events).

### Технологічний стек

| Шар | Технологія |
|-----|-----------|
| Сервер | Node.js, Fastify 5 |
| Шаблони / UI | EJS, HTMX, Server-Sent Events |
| База даних | PostgreSQL (`pg`), нумеровані SQL-міграції |
| Обробка зображень | sharp (видалення фону, композитинг, векторні SVG-плашки) |
| AI | OpenAI API (генерація описів; опціонально) |
| Інфраструктура | Docker Compose (db + app) |
| Тести | Vitest |

### Структура репозиторію

```
src/
  parser/              Парсери прайсів (per-стандарт) + спільне збереження в БД
    manager/           Парсер формату Manager
    shared/            save-oils — єдина логіка upsert + diff + історія цін
  photos/
    process/           Обробка фото: шаблони, векторні плашки, композитинг
    import/            Імпорт фото EUROLUB (матч за артикулом)
    import-manager/    Імпорт фото Manager (матч за артикулом + об'ємом)
    browser-tool/      Шаблони тари (каністри/бочки/відра)
  integrations/
    truckmarket/       Клієнт API, оркестратор публікації, мапінг полів
    openai/            Генератор описів, промпти, system-prompt
  web/
    routes/            HTTP-маршрути (import, oils, companies, jobs, prompts...)
    services/          JobRunner — фонові задачі з логами й скасуванням
    repositories/      Доступ до БД (users, jobs)
    views/             EJS-шаблони
    view-helpers.js    Переклад статусів + форматування дат (Київський час)
  shared/infra/        Пул з'єднань до БД
database/
  migrations/          Нумеровані міграції (порядок гарантовано)
  seeds/               Базові інтеграції
tests/                 Vitest (180+ тестів)
```

## Модель даних

Каталог будується навколо кількох ключових таблиць:

- **`company_olivs`** — компанія-постачальник (назва, країна, місто, шляхи до
  останнього прайсу й папки фото).
- **`olivs`** — олива. Унікальна за парою `(company_id, articul)` — артикул є
  природним ключем для розпізнавання змін при повторному імпорті. Містить
  характеристики (в'язкість SAE, ACEA, API, допуски, об'єм тари тощо), бренд,
  місто й посилання на інтеграцію.
- **`oils_price`** — історія цін. Кожна зміна ціни закриває попередній запис
  (`valid_to`) і відкриває новий — повна хронологія без втрат.
- **`oils_images`** — фотографії з прив'язкою до оливи й статусом обробки.
- **`integrations`** — реєстр джерел даних (див. нижче).
- **`web_jobs`** — фонові задачі: тип, статус, лог, зведення результату.
- **`ai_prompts`** — промпти для генерації описів (із позначкою «дефолтний»).

## Core logic

### Інтеграції як джерело правди

Центральна концепція: **інтеграція** — це опис того, звідки беруться дані для
конкретного стандарту прайсу. Різні постачальники по-різному заповнюють файли:
у когось бренд указаний у назві, у когось — окремою колонкою; місто може бути
фіксованим або задаватися вручну на сайті.

Замість того щоб «зашивати» ці правила в код кожного парсера, вони описані
декларативно в таблиці `integrations`:

| Поле | Призначення |
|------|-------------|
| `code` | Стабільний ключ (`EUROLUB`, `ManagerIntegration`) |
| `brand_source` | Звідки бренд: `parser` (з файлу/фіксований) чи `web` |
| `city_source` | Звідки місто: `parser` чи `web` (вручну per-товар) |
| `default_brand` | Фіксований бренд, коли `brand_source = parser` |
| `default_city` | Фіксоване місто, коли `city_source = parser` |

Парсер читає цей рядок і застосовує правила під час збереження. Додати нового
постачальника — це новий парсер формату плюс запис у `integrations`; решта
конвеєра (історія цін, обробка фото, публікація) працює без змін.

Приклади налаштованих інтеграцій:

- **EUROLUB** — бренд фіксований (`parser` → «EUROLUB»), місто задається на
  сайті для кожного товару.
- **ManagerIntegration** — бренд із колонки прайсу, місто фіксоване (Луцьк).

### Розумний імпорт і diff

Повторний імпорт того самого прайсу — це не перезапис, а **звірка змін**. Логіка
зосереджена в одному місці (`save-oils`) і однакова для всіх інтеграцій:

- **Нова позиція** (артикул відсутній у БД) — створюється.
- **Наявна позиція** — оновлюються характеристики.
- **Ціна** — якщо змінилась, попередній запис історії закривається, відкривається
  новий; якщо не змінилась — історія не торкається.
- **Уже опублікований товар зі зміненою ціною** — позначається статусом
  `outdated`, щоб згодом оновити оголошення на маркетплейсі.

Підтримується також режим **«тільки фото»**: можна донести папку зображень без
прайсу — система зіставить їх із наявними оливами (за артикулом, а для Manager —
за артикулом плюс об'ємом) і обробить лише нові.

Кожен імпорт повертає **картку-зведення**: скільки створено, оновлено, змінено
цін, скільки без змін, скільки фото додано й оброблено.

### Обробка фотографій

Маркетплейс очікує фото в єдиному вигляді: товар на стандартному шаблоні тари з
інформаційними плашками (об'єм, тип). Конвеєр обробки (`sharp`):

1. Визначає тип тари й об'єм **за даними БД** (не за іменем файлу) — однаково
   надійно для всіх інтеграцій.
2. Видаляє білий фон вихідної фотографії та обрізає за межами товару.
3. Вписує товар у відповідний шаблон тари.
4. Накладає **векторні (SVG) плашки** з об'ємом — чіткий текст без розмиття
   (растрові плашки на маленьких шаблонах розмивалися при стисканні).
5. Зберігає результат у високій якості (JPEG 95, chroma 4:4:4).

Обробка інкрементальна — переобробляються лише нові або раніше невдалі
зображення.

### AI-описи

Опис товару генерується з **усіх** його характеристик через OpenAI. Промпт
зберігається в БД і редагується через веб-панель; є **симулятор** — можна вибрати
оливу й побачити згенерований опис, нічого не зберігаючи. За відсутності
API-ключа AI-функції просто вимикаються, решта системи працює.

### Публікація на TruckMarket

Оркестратор формує картку оголошення під вимоги API маркетплейсу:

- **Мапінг полів** — характеристики оливи перекладаються в коди полів TruckMarket.
  Коди різняться за категоріями (моторні / трансмісійні / гідравлічні) і
  обробляються відповідно.
- **Бренд** — зіставлення назви бренду з ID маркетплейсу, нечутливе до регістру,
  з урахуванням синонімів написання.
- **Геолокація** — місто визначається за назвою через API (пошук ID регіону),
  береться з компанії оголошення.
- **Фото** — завантажуються оброблені зображення; товар без жодного фото не
  публікується.
- **Статуси** — `pending` / `in_progress` / `done` / `outdated` / `failed`
  відображаються в каталозі; застарілі оголошення можна оновити одним рухом.

### Фонові задачі й контроль

Будь-яка важка операція (імпорт, публікація, видалення з маркетплейсу) виконується
через **JobRunner**:

- статуси записуються в `web_jobs`, лог стрімиться в браузер через SSE;
- кожен рядок логу має часову мітку (Київський час), задача має банери старту,
  завершення й тривалості;
- задачу можна скасувати (сигнал дочірнім процесам);
- одночасність обмежена семафором; «осиротілі» після рестарту задачі
  автоматично закриваються.

Інтерфейс повністю україномовний; статуси й дати перекладаються та форматуються
централізовано через `view-helpers`, час показується за Києвом.

## Запуск

### Через Docker (рекомендовано)

```bash
cp .env.example .env        # заповнити значення (БД, TruckMarket, OpenAI, SESSION_SECRET)
make init                   # підняти стек + міграції + базові інтеграції
make create-user U=admin P=ваш_пароль
```

Панель доступна на `http://localhost:3000`.

### Корисні команди (Makefile)

| Команда | Дія |
|---------|-----|
| `make up` / `make down` | Підняти / зупинити стек |
| `make logs` | Логи app (follow) |
| `make migrate` | Прогнати міграції по порядку |
| `make seed-integrations` | Додати базові інтеграції (ідемпотентно) |
| `make psql` | psql до БД у контейнері |
| `make create-user U=.. P=..` | Створити веб-користувача |
| `make backup-db` | Дамп БД у `backup.sql` |
| `make test` | Запустити тести |

## Конфігурація

Усі секрети — у `.env` (не комітиться). Шаблон — `.env.example`.

| Група | Змінні |
|-------|--------|
| PostgreSQL | `PG_HOST`, `PG_PORT`, `PG_DB`, `PG_USER`, `PG_PASSWORD` |
| TruckMarket | `TRUCK_BASE_URL`, `KEY_ID`, `SECRET_KEY`, `USER_ID`, `COMPANY_ID`, `GEO_CITY_ID_DEFAULT` |
| OpenAI (опц.) | `OPENAI_API_KEY`, `OPENAI_MODEL` |
| Веб | `PORT`, `HOST`, `SESSION_SECRET`, `NODE_ENV` |
| Час | `TZ`, `UI_TZ` (за замовчуванням `Europe/Kyiv`) |

## Тестування

```bash
npm test            # усі тести

```

обробка статусів і дат, рендеринг шаблонів, фоновий JobRunner.

## Безпека

- Паролі користувачів хешуються (bcrypt); сесії — на підписаних cookie.
- Секрети не зберігаються в репозиторії; `.env`, прайси та вхідні фото
  виключені через `.gitignore`.
- Доступ до панелі — лише автентифікованим користувачам.
